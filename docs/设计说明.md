# 设计说明：为什么这样做，以及哪些没做

这份文档只写取舍，不写功能清单（功能在 `使用说明`）。每条都对应一个具体代价。

---

## 一、为什么是独立插件，不并进认知核心

认知核心的定位是"她是谁、她记得什么"——对话记忆，注入到每轮上下文。学习管线是另一条链路：**离线、按需、量大、且常常几周不动一次**。

并进去会有三个具体问题：

1. **注入路径被拖慢**。核心每轮都要取记忆，学习数据是几万字的正文，放同一个库里，检索会从毫秒级变成需要分页。
2. **额度语义冲突**。核心的写入是"对话自动发生"，手账是"每天 2 篇、必须有人决定写什么"。两种节奏混在一个 store 里，去重和限额都会互相干扰。
3. **卸载成本**。核心是常驻能力，学习管线是可选玩具。装在一起，不想用的人也得背着它的代码和数据。

所以：独立目录、独立数据、独立开关，默认关闭。**不 import 核心任何模块**——核心没装也能跑（`test/manifest.test.mjs` 里有一条测试守着"不许引入外部包"）。

---

## 二、手账为什么是"账本 + 索引 + 分卷"，不是 SQLite

参考实现（dsh-bili-humanism）用 SQLite，是为了解决 90KB / 950 行读取被截断的问题，代价是事务、迁移、以及"数据库文件坏了只能重建"。

我们这边量级是几千条，几个入口：

```text
ledger.jsonl   唯一真相，append-only，一行一篇
index.json     派生：总篇数、分卷表、快照（可删，会重建）
volumes/v-*.md 派生：按 24KB / 350 行切卷（可删，会重建）
```

三条不变量，每次读取都校验：

```text
1. 索引 total == 账本条数
2. 各卷 count 之和 == total
3. 每个 id 在所有卷里恰好出现一次
```

好处是**人能救**：账本是纯文本，出问题可以直接看、直接改一行。坏处也说清楚：没有事务，写入靠单进程串行；如果哪天有两个进程同时写，账本会坏——所以约定只有一个写入者（宿主进程内），不做跨进程锁，也不假装做了。

---

## 三、为什么要"快照"

分卷是派生数据，读的时候可能正好有人在写新手账，导致"读到的卷是旧的、索引是新的"。

所以 `index` 返回一个快照（`sha256(total:lastId:lastAt)` 前 16 位），`readVolume` 必须带这个快照。不一致就抛 `STALE_SNAPSHOT`，让调用方重新取索引。**宁可让模型多调一次工具，也不让它拿着一半新一半旧的数据编故事。**

---

## 四、额度为什么数账本，不用计数文件

计数文件会在"写入成功但计数没写"时漂移，重启也会重置。账本里每篇都有 `day` 字段，数一遍就是准确值——几千行文本，读一遍不到 10ms。

代价：每次写手账都要全量读账本。等真的到十万条再说，现在不做预优化。

---

## 五、没有做 ASR：不是不会，是不该塞进插件

实测（2026-10-31）：匿名能直接下载 B站音频流（5.9MB / HTTP 200），所以"下载音频"这步没有障碍。真正的问题是转写：

```text
要模型文件（whisper.cpp / sherpa-onnx，几百 MB 到 1GB+）
要 CPU 时间（1 小时视频在普通机器上几分钟到几十分钟）
要额外的可执行文件或原生依赖
```

这三样和"零依赖、宿主进程内、随插件加载"是冲突的：一个下载 1GB 模型的插件，不该在用户点开面板时偷偷跑。

所以本插件**只做有字幕的稿**，没有字幕就如实标 `metadata-only`。如果哪天要做 ASR，正确形态是一个独立 sidecar（外部程序 + 显式命令），不是塞进这个插件。

---

## 六、没有做"自动提问 / 自动摘要"：没有模型就不装

参考实现有"观影后提问"和"人格札记"，它们背后是 LLM。这个插件没有 LLM：

- **自动摘要**：规则摘要只能做"每 5 分钟挑最长的一句"，那已经做成了时间轴要点。再往上叫"摘要"就是骗人。
- **自动提问**：没有上下文的提问模板产出的是"你觉得这个视频怎么样？"这种废话，占 token 又没用。

所以：简报只做**指路**（时间轴 + 高频词 + 数字术语），观点由模型或人写进手账。工具描述里也写明了"它指路，不是结论"。

---

## 七、检索为什么不做向量 / 同义改写

核心插件那边量过：语义向量的正样本最小相似度 0.114、负样本最大 0.484，**没有可用阈值**；强行接上，负例误纳从 4/10 掉到 0/10。

学习管线的查询形态更简单——"上次那篇讲凭证的"，字面就能命中。加同义表和向量只会让"为什么这条被搜出来"变得没法解释。所以这里用最朴素的 BM25（中文 bigram + 英文词），命中就给片段，没命中就返回空数组。

---

## 八、安全边界

```text
SESSDATA      只存本地 config，只发给 *.bilibili.com（hostAllowedForCookie 判定），
              任何快照、日志、错误信息都不回显原文，面板只显示"有/没有"
网络          只有 bilibili.com 与它的字幕 CDN 域名
写入          只写 data/plugin-data/cognition-study/ 与自己的 panel/ 快照
工具          全部 owner-only；未绑定主人时一律拒绝
```

不做的事：不自动抓取（没有定时任务）、不主动发消息、不注入上下文（`hooks = {}`）。

## 九、字幕接口的实测记录（2026-10-31）

```text
匿名 × 16 个样本     player/v2 与 wbi/v2 都返回 code 0，但 subtitles 为空，
                    subtitle 对象只剩 allow_submit / lan / lan_doc / subtitles，
                    allow_submit=false、lan 为空 → 登录态被裁掉，不是"视频没字幕"。
匿名 + WBI 签名     仍然为空。所以不是签名问题，是登录门槛。
带 SESSDATA         同一批样本立刻返回 ai-zh（AI 字幕），例如
                    BV1UbyZB9ERb 第 1P：260–416 段 / 2550–5074 字。
短时间连续请求      会出现 code 0 + 空数组（限流），隔一会儿再问又有；
                    插件因此对"有登录态却空列表"重试一次，并标 NONE_MAYBE_THROTTLED。
```

顺带记一个真实数据的形状：AI 字幕**没有标点**，是按停顿切开的词串。
第一版要点直接取"窗口内最长的一句"，结果吐出一条 200 多字的无标点长墙。
现在先按空格/标点切成 15–70 字的短句，再按"不同词数 + 长度封顶"选每窗最密的一条——
这是被真实样本逼出来的改动，不是拍脑袋。

## 十、手账能改，但不能编辑

手账最需要的是"改主意"，最危险的也是"改主意"。

```text
直接覆盖   三个月后你不知道当时为什么那么想；账本里只有一个版本，判断过程被抹掉了
不接受修改 记错了字、写错了 id 也没法补，最后只能删文件重来
```

所以：**追加修订**。新条目带 `revises` 指向原 id，原条目一个字不动。

```text
列表    每条显示"有几条修订 / 最新标题"
读一篇  原条目在前，修订按时间正序在后
导出    修订以引用块跟在原条目下面，标"修订于 <时间>"
额度    修订不占——它不是新的一天的想法，是改错字
校验    修订指向的原条目不存在 → 算孤儿，verify 报出来
```

为什么孤儿也要管：修订是"挂在"原条目上的，如果原 id 打错，这条修订永远不会出现在任何列表里——
等于写了个没人看得见的东西。写入时校验一次（拒绝），校验时再查一次（报错），两道都挡。

### 为什么额度加到"字数"

原来只有"每天 2 篇"。但 2 × 8000 字 = 16000 字/天，账本一年能长到几 MB，
而且是那种"每篇写满再说"的写法堆出来的。加一道 6000 字/天：

```text
篇数闸  防"一天写八篇流水账"
字数闸  防"两篇各写八千字"
```

两道都按账本统计，重启不重置。超了就说清楚已经写了多少，读取、检索、导出完全不受影响。

### 读卷为什么要分页

一卷最多 24KB / 350 行。听起来不大，但整卷塞进上下文仍会挤掉真正要用的东西。
读卷默认 6000 字/页，返回 `nextOffset`；只有读到底才返回 `nextVolume`。
"下一页"和"下一卷"分开，模型才不会漏掉半卷就跳走。

### 修复工具为什么只重建派生文件

```text
账本 ledger.jsonl   唯一真相，永远不自动改写
索引 index.json     派生，坏了重建
分卷 volumes/*.md   派生，坏了重建
```

`study_journal_repair` 做的事：校验一次 → 重建派生 → 再校验一次，把"修好了什么"如实返回。
不做"自动删除异常条目"这种事——手账里的东西是人写的，删不删由人决定。

## 十一、已知缺口（按优先级）

```text
1. 无 ASR          见第五节。音频能下，模型不该塞进插件。
2. 无分P 批量取稿  一次一个 P，合集要逐个取。
3. 手账无编辑      故意的：要改就写新的一篇，旧的不动（append-only）。
4. 无导出          手账在文本文件里，直接复制即可；没做专门的导出命令。
5. 面板视觉未验收  逻辑有 5 条测试覆盖；这台机器的模型读不了图，
                  所以布局/字号/对比度没有经过我这一侧的视觉检查。
6. AI 字幕会波动   同一 P 两次取稿的段数/字数可能不同（B站端生成），
                  重复取稿保留首份、正文不覆盖——这是取舍，不是 bug。
```
